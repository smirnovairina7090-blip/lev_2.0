# Урок: уникальный дроп Crystal Spider

Версия проекта: Minecraft 1.21.1, Fabric, Mojang mappings.

## Результат урока

После урока ученик сможет объяснить, что такое loot table, создать отдельный дроп для собственного моба и менять количество предметов и вероятность выпадения без переписывания Java-класса сущности.

Наш Crystal Spider после смерти:
- всегда роняет 1-3 осколка аметиста;
- с вероятностью 5% дополнительно роняет 1 блок аметиста;
- с вероятностью 10% дополнительно роняет 1 кальцит.

Важно: блок аметиста и кальцит проверяются независимо. Теоретически в одной смерти могут выпасть оба редких предмета.

## Главная идея урока

Начать не с кода, а с вопроса:

> Где логичнее хранить правило "что выпадает после смерти": внутри Java-класса паука или в отдельном файле с данными?

Подвести к мысли: поведение моба и его таблица наград - разные задачи.

CrystalSpider.java отвечает за поведение сущности: получение урона, обратный урон, AI и другие действия.

Loot table отвечает за предметы, которые Minecraft генерирует после смерти сущности.

Это хороший пример data-driven подхода: мы не зашиваем все настройки в Java, а часть игрового контента описываем данными.

## Что показать перед кодом

Лучше не включать длинный фильм. Для этого урока полезнее короткое демо на 30-60 секунд:

1. Убить обычного паука и посмотреть его дроп.
2. Убить Crystal Spider.
3. Спросить: "Как Minecraft вообще решает, что сейчас должно выпасть?"
4. Показать схему:

```text
Crystal Spider погиб
        ↓
Minecraft ищет его loot table
        ↓
entities/crystal_spider.json
        ↓
проверяет каждый pool
        ↓
создаёт предметы
```

Если хочется визуального крючка, можно заранее показать на экране три карточки:
- осколок аметиста - обычный дроп;
- кальцит - редкий дроп;
- блок аметиста - очень редкий дроп.

И попросить ученика самому назначить проценты, а потом сравнить с нашей версией.

## Где создаём файл

В Minecraft 1.21.1 каталог называется `loot_table` в единственном числе.

Полный путь:

```text
src
└── main
    └── resources
        └── data
            └── azazels-alchemy-table
                └── loot_table
                    └── entities
                        └── crystal_spider.json
```

Почему имя именно `crystal_spider.json`?

Потому что сущность зарегистрирована как:

```text
azazels-alchemy-table:crystal_spider
```

Для дропа сущности Minecraft ищет таблицу в категории `entities` с тем же именем.

## Полный рабочий код

Файл:

```text
src/main/resources/data/azazels-alchemy-table/loot_table/entities/crystal_spider.json
```

Код:

```json
{
  "type": "minecraft:entity",
  "pools": [
    {
      "rolls": 1,
      "entries": [
        {
          "type": "minecraft:item",
          "name": "minecraft:amethyst_shard",
          "functions": [
            {
              "function": "minecraft:set_count",
              "count": {
                "type": "minecraft:uniform",
                "min": 1,
                "max": 3
              }
            }
          ]
        }
      ]
    },
    {
      "rolls": 1,
      "entries": [
        {
          "type": "minecraft:item",
          "name": "minecraft:amethyst_block",
          "conditions": [
            {
              "condition": "minecraft:random_chance",
              "chance": 0.05
            }
          ]
        }
      ]
    },
    {
      "rolls": 1,
      "entries": [
        {
          "type": "minecraft:item",
          "name": "minecraft:calcite",
          "conditions": [
            {
              "condition": "minecraft:random_chance",
              "chance": 0.10
            }
          ]
        }
      ]
    }
  ]
}
```

## Разбираем код очень просто

### 1. type

```json
"type": "minecraft:entity"
```

Мы говорим Minecraft:

> Эта таблица предназначена для дропа сущности.

Вопрос ученику:

> Какой `type` мог бы быть у таблицы сундука или блока? Почему Minecraft полезно знать контекст?

Необязательно сразу знать точный ответ. Здесь важна идея: одна и та же система loot table используется в разных ситуациях.

### 2. pools

```json
"pools": [
    ...
]
```

`pool` можно представить как отдельную коробку с правилами розыгрыша.

У нас три независимые коробки:

```text
POOL 1 → осколки аметиста
POOL 2 → шанс на блок аметиста
POOL 3 → шанс на кальцит
```

Лайфхак для объяснения:

Возьми три воображаемых автомата. Когда паук погибает, Minecraft запускает все три автомата по очереди.

### 3. rolls

```json
"rolls": 1
```

Это количество попыток этого pool.

`1` означает:

> Проведи розыгрыш один раз.

Вопрос:

> Что произойдёт, если поставить `rolls: 3`?

Хорошая гипотеза ученика: pool будет разыгран три раза, поэтому один и тот же предмет может генерироваться несколько раз.

### 4. entries

```json
"entries": [
    {
        "type": "minecraft:item",
        "name": "minecraft:amethyst_shard"
    }
]
```

`entries` - кандидаты на выпадение.

```json
"type": "minecraft:item"
```

означает, что результатом будет предмет.

```json
"name": "minecraft:amethyst_shard"
```

указывает конкретный предмет.

Мини-вопрос:

> Что нужно поменять, если вместо осколка мы захотим алмаз?

Ответ:

```json
"name": "minecraft:diamond"
```

Это хороший момент показать, что большая часть настройки дропа делается изменением данных, а не Java.

## Как получается 1-3 осколка

Эту часть делает функция:

```json
"functions": [
  {
    "function": "minecraft:set_count",
    "count": {
      "type": "minecraft:uniform",
      "min": 1,
      "max": 3
    }
  }
]
```

`set_count` - установить количество предметов.

`uniform` - случайно выбрать значение из диапазона.

```text
min = 1
max = 3
```

В нашем случае возможны:

```text
1 осколок
2 осколка
3 осколка
```

Практический вопрос:

> Если мы хотим сделать паука щедрее, где менять код?

Например:

```json
"min": 2,
"max": 5
```

## Как работает вероятность

Для блока аметиста:

```json
{
  "condition": "minecraft:random_chance",
  "chance": 0.05
}
```

`0.05` = 5%.

Удобная шпаргалка:

```text
0.50 = 50%
0.25 = 25%
0.10 = 10%
0.05 = 5%
0.01 = 1%
```

Для кальцита:

```json
"chance": 0.10
```

то есть 10%.

Вопрос:

> Что должно выпадать чаще: кальцит или блок аметиста?

Ответ: кальцит, потому что 10% больше 5%.

## Математика прямо внутри GameDev

Пусть мы победили 100 Crystal Spider.

В среднем ожидаем примерно:

```text
осколки:
среднее между 1 и 3 ≈ 2
100 × 2 ≈ 200 осколков

блок аметиста:
100 × 0.05 ≈ 5 блоков

кальцит:
100 × 0.10 ≈ 10 блоков
```

Но это не обещание.

Очень важный вопрос для обсуждения:

> Если шанс 5%, обязан ли блок выпасть ровно 5 раз из 100?

Нет. Вероятность описывает случайный процесс. В конкретной серии может выпасть 2, 7 или вообще 0. Чем больше испытаний, тем обычно ближе результат к ожидаемой доле.

Это хороший мостик к вероятности в математике.

## Почему редкие предметы находятся в разных pools

Потому что мы хотим две независимые проверки:

```text
Выпал блок аметиста?  да / нет

и отдельно

Выпал кальцит?        да / нет
```

Поэтому возможна редкая ситуация:

```text
осколки + блок аметиста + кальцит
```

Вопрос ученику:

> Это баг или игровая механика?

Ответ зависит от дизайна. Сейчас это сознательная механика.

## Вариант 1. Сделать редкий дроп заметнее во время тестов

Во время разработки 5% неудобны: можно убить много пауков и решить, что код сломан.

Лайфхак разработчика:

На время теста поставить:

```json
"chance": 1.0
```

Это 100%.

Убедились, что предмет действительно выпадает - возвращаем нужную вероятность.

Ещё хороший тестовый вариант:

```text
amethyst_block = 0.50
calcite        = 0.50
```

После проверки обязательно вернуть баланс.

## Вариант 2. Изменить баланс без изменения структуры

Более щедрый паук:

```text
осколки: 2-5
блок аметиста: 10%
кальцит: 20%
```

Более редкий и ценный:

```text
осколки: 1-2
блок аметиста: 2%
кальцит: 5%
```

Задание ученику:

> Придумай Easy, Normal и Hard версии дропа. Объясни, почему выбрал именно такие проценты.

## Вариант 3. Редкий предмет только один

В нашей основной версии кальцит и блок аметиста могут выпасть одновременно.

Если дизайн требует максимум один редкий предмет, можно заменить два редких pool одним взвешенным pool:

```json
{
  "rolls": 1,
  "entries": [
    {
      "type": "minecraft:item",
      "name": "minecraft:amethyst_block",
      "weight": 1
    },
    {
      "type": "minecraft:item",
      "name": "minecraft:calcite",
      "weight": 2
    },
    {
      "type": "minecraft:empty",
      "weight": 17
    }
  ]
}
```

Общий вес:

```text
1 + 2 + 17 = 20
```

Поэтому:

```text
amethyst_block = 1 / 20 = 5%
calcite        = 2 / 20 = 10%
ничего редкого = 17 / 20 = 85%
```

И теперь из этого pool за одну попытку выбирается только один результат.

Сильный вопрос:

> Чем этот вариант отличается от двух независимых `random_chance`?

Это уже настоящее проектирование игровой механики, а не просто написание JSON.

## Вариант 4. Дроп только если победил игрок

Можно добавить условие:

```json
"conditions": [
  {
    "condition": "minecraft:killed_by_player"
  }
]
```

Тогда конкретный pool будет работать только при убийстве, которое засчитывается игроку.

Вопрос:

> Зачем разработчику такое ограничение?

Возможные ответы:
- чтобы нельзя было построить слишком простую автоматическую ферму;
- чтобы редкая награда требовала участия игрока;
- чтобы контролировать экономику предметов.

## Вариант 5. Looting как следующий уровень

В Minecraft 1.21 система loot table умеет учитывать зачарования. Для следующего занятия можно сделать так, чтобы Looting:
- увеличивал количество осколков;
- повышал шанс редкого предмета.

Не добавляем это в первую рабочую версию: сначала ученик должен увидеть и понять обычные `pool`, `entry`, `function` и `condition`.

Это хороший принцип разработки:

> Сначала минимальная рабочая механика, потом одно усложнение за раз.

## Что НЕ нужно добавлять в CrystalSpider.java

Для нашей базовой версии в Java не нужно писать:

```java
spawnAtLocation(...)
```

не нужно вручную создавать:

```java
new ItemStack(...)
```

и не нужно делать:

```java
Random
```

для каждой награды.

Minecraft уже имеет систему loot table специально для этой задачи.

Хороший вопрос:

> Почему готовая система лучше собственного случайного кода в `die()`?

Ответы:
- меньше Java-кода;
- легче менять баланс;
- данные отделены от поведения;
- проще читать;
- проще расширять;
- лучше совместимость с Minecraft-механиками.

## Как проверить в Minecraft

Сначала собираем новый JAR и убеждаемся, что GitHub Actions зелёный.

Затем:

```text
/summon azazels-alchemy-table:crystal_spider ~2 ~ ~
```

Убиваем паука.

Ожидаем:
- 1-3 осколка аметиста всегда;
- иногда кальцит;
- очень редко блок аметиста.

Для проверки вероятностей не делаем вывод по одной смерти.

Удобная схема теста:

```text
Тест 1: 5 пауков
Проверяем, что осколки вообще работают.

Тест 2: временно ставим редкому предмету chance = 1.0
Проверяем, что путь и ID предмета правильные.

Тест 3: возвращаем 0.05 и 0.10
Проверяем финальный игровой баланс.
```

## Отладка: если ничего не выпадает

Проверяем по порядку.

### 1. Путь

Должно быть:

```text
data/azazels-alchemy-table/loot_table/entities/crystal_spider.json
```

Для Minecraft 1.21.1 важно именно `loot_table`, а не старое `loot_tables`.

### 2. Имя файла

```text
crystal_spider.json
```

должно совпадать с ID сущности:

```text
azazels-alchemy-table:crystal_spider
```

### 3. JSON

Самые частые ошибки:
- забытая запятая;
- лишняя запятая;
- незакрытая `}`;
- незакрытая `]`;
- неправильный ID предмета.

### 4. Проверяем сначала 100% шанс

Если при:

```json
"chance": 1.0
```

предмет всё равно не появляется, проблема не в случайности.

### 5. Проверяем свежий JAR

Очень частая ловушка:

> Код исправили, а Minecraft запустили со старым JAR.

Всегда сверяем, что взяли артефакт из последней успешной сборки.

Если предмет не выпал 20 раз подряд, это ещё не доказательство ошибки.

# Улучшение дропа: Looting I → II → III

Это следующий маленький шаг. Мы НЕ переписываем весь loot table и НЕ трогаем редкий дроп. Улучшаем только первый pool, где уже выпадают осколки аметиста.

## Идея

Сейчас первая функция уже делает базовое количество:

```json
{
  "function": "minecraft:set_count",
  "count": {
    "type": "minecraft:uniform",
    "min": 1,
    "max": 3
  }
}
```

Она означает:

```text
без Looting → 1-3 осколка
```

Теперь мы хотим сказать Minecraft:

> После того как базовое количество уже выбрано, посмотри уровень Looting на оружии убийцы и добавь ещё предметы.

Для этого НЕ удаляем `set_count`. Сразу после него добавляем вторую функцию:

```json
{
  "function": "minecraft:enchanted_count_increase",
  "enchantment": "minecraft:looting",
  "count": {
    "type": "minecraft:uniform",
    "min": 1,
    "max": 1
  }
}
```

### Что здесь новое

```json
"function": "minecraft:enchanted_count_increase"
```

Это готовая функция Minecraft:

> увеличь количество дропа в зависимости от уровня указанного зачарования.

Следующая строка:

```json
"enchantment": "minecraft:looting"
```

говорит:

> Следи именно за зачарованием Looting.

А:

```json
"min": 1,
"max": 1
```

означает, что каждый уровень Looting добавляет ровно 1 дополнительный осколок.

Получается наша игровая механика:

```text
без Looting → 1-3 осколка

Looting I
→ базовые 1-3
→ +1
→ итого 2-4

Looting II
→ базовые 1-3
→ +2
→ итого 3-5

Looting III
→ базовые 1-3
→ +3
→ итого 4-6
```

## Где именно вставлять

Открываем:

```text
src/main/resources/data/azazels-alchemy-table/loot_table/entities/crystal_spider.json
```

Находим ТОЛЬКО первый предмет:

```json
"name": "minecraft:amethyst_shard"
```

Ниже у него уже есть:

```json
"functions": [
  {
    "function": "minecraft:set_count",
    "count": {
      "type": "minecraft:uniform",
      "min": 1,
      "max": 3
    }
  }
]
```

Не стираем этот блок.

После закрывающей `}` функции `set_count` ставим запятую и добавляем новую функцию.

Было:

```json
"functions": [
  {
    "function": "minecraft:set_count",
    "count": {
      "type": "minecraft:uniform",
      "min": 1,
      "max": 3
    }
  }
]
```

Стало:

```json
"functions": [
  {
    "function": "minecraft:set_count",
    "count": {
      "type": "minecraft:uniform",
      "min": 1,
      "max": 3
    }
  },
  {
    "function": "minecraft:enchanted_count_increase",
    "enchantment": "minecraft:looting",
    "count": {
      "type": "minecraft:uniform",
      "min": 1,
      "max": 1
    }
  }
]
```

То есть реально добавили только ОДИН новый объект в уже существующий массив `functions`.

## Почему здесь две функции подряд

Это полезный вопрос ученику:

> Minecraft сначала выбирает количество 1-3 или сначала смотрит Looting?

В нашем файле функции идут сверху вниз.

Сначала:

```text
set_count
↓
выбрали базу 1-3
```

Потом:

```text
enchanted_count_increase
↓
прибавили бонус Looting
```

Можно проговорить как формулу:

```text
финальный дроп = базовый дроп + бонус Looting
```

Например:

```text
Minecraft выбрал 2 осколка
+
меч имеет Looting III
+
добавляем 3
=
5 осколков
```

## Почему мы НЕ меняем amethyst_block и calcite

На этом шаге Looting влияет только на обычные осколки.

Это сознательное решение дизайна.

Редкие предметы пока остаются:

```text
amethyst_block = 5%
calcite = 10%
```

Вопрос для обсуждения:

> Должен ли Looting III ещё и увеличивать шанс блока аметиста?

Здесь нет единственного правильного ответа.

Вариант А:
- Looting увеличивает только количество обычного ресурса;
- редкие предметы остаются действительно редкими.

Вариант Б:
- Looting увеличивает и шанс редких предметов;
- зачарование становится намного ценнее.

Это можно оставить как следующее улучшение.

## Важно: комментарии внутри JSON

В рабочий `crystal_spider.json` нельзя вставлять строки вида:

```text
// Looting добавляет осколки
```

Обычный JSON комментарии не поддерживает, и такой комментарий сломает файл.

Поэтому комментарии и объяснения храним в этой методичке, а рабочий JSON оставляем чистым.

## Как тестировать в Minecraft

Лучше сравнить четыре оружия:

```text
обычный меч
Looting I
Looting II
Looting III
```

Для чистого теста можно выдать себе мечи командами или взять их через Creative.

Проверяем не один бой, а несколько, потому что базовое количество всё равно случайное: 1-3.

Ожидаемые диапазоны:

```text
без Looting → 1-3
Looting I   → 2-4
Looting II  → 3-5
Looting III → 4-6
```

Если Looting III всё равно даёт максимум 3, сначала проверяем:
- взяли ли свежий JAR;
- точно ли паука убил игрок;
- действительно ли оружие имеет Looting;
- лежит ли функция внутри `functions` именно у `amethyst_shard`.

## Следующий возможный уровень

Когда это заработало, можно задать вопрос:

> А можем ли мы сделать Looting влияющим не на количество, а на шанс редкого предмета?

Да. В Minecraft 1.21 для этого есть механика `random_chance_with_enchanted_bonus`. Но её лучше добавлять отдельным следующим шагом, чтобы сейчас не смешивать две идеи: количество и вероятность.

# Улучшение 2: Looting повышает шанс редкого дропа

Это продолжение предыдущего шага. Мы НЕ переписываем весь loot table, НЕ трогаем базовый дроп осколков и НЕ меняем механику обратного урона паука.

На прошлом шаге Looting уже увеличивал КОЛИЧЕСТВО осколков:

```text
без Looting → 1-3
Looting I   → 2-4
Looting II  → 3-5
Looting III → 4-6
```

Теперь добавляем вторую идею:

> Looting может влиять не только на количество обычного ресурса, но и на ВЕРОЯТНОСТЬ редкой награды.

## Какой баланс делаем

Для блока аметиста:

```text
без Looting → 5%
Looting I   → 6%
Looting II  → 7%
Looting III → 8%
```

Для кальцита:

```text
без Looting → 10%
Looting I   → 12%
Looting II  → 14%
Looting III → 16%
```

Почему бонус небольшой?

Потому что редкий предмет должен оставаться редким. Looting помогает, но не превращает 5% в почти гарантированный дроп.

## Что меняем в файле

Открываем:

```text
src/main/resources/data/azazels-alchemy-table/loot_table/entities/crystal_spider.json
```

У нас уже есть отдельный pool блока аметиста и отдельный pool кальцита.

Мы НЕ удаляем сами предметы и НЕ меняем `rolls`.

Меняем только условие вероятности внутри `conditions`.

---

## Шаг 1. Улучшаем шанс блока аметиста

### Было

```json
"conditions": [
  {
    "condition": "minecraft:random_chance",
    "chance": 0.05
  }
]
```

Это простое правило:

> Всегда используй один и тот же шанс 5%.

### Стало

```json
"conditions": [
  {
    "condition": "minecraft:random_chance_with_enchanted_bonus",
    "enchantment": "minecraft:looting",
    "unenchanted_chance": 0.05,
    "enchanted_chance": {
      "type": "minecraft:linear",
      "base": 0.06,
      "per_level_above_first": 0.01
    }
  }
]
```

Мы заменили только ОДИН объект условия.

### Что означает каждая новая строка

```json
"condition": "minecraft:random_chance_with_enchanted_bonus"
```

Это условие говорит Minecraft:

> Проверяй случайный шанс, но умей менять его в зависимости от зачарования.

```json
"enchantment": "minecraft:looting"
```

Это говорит:

> Нас интересует именно Looting.

```json
"unenchanted_chance": 0.05
```

Если Looting нет:

```text
0.05 = 5%
```

То есть старое поведение мы сохранили.

Дальше:

```json
"enchanted_chance": {
  "type": "minecraft:linear",
  "base": 0.06,
  "per_level_above_first": 0.01
}
```

Это формула для зачарованного оружия.

`linear` означает линейный рост:

```text
шанс = base + per_level_above_first × (уровень - 1)
```

Для нашего блока аметиста:

```text
Looting I:
0.06 + 0.01 × 0 = 0.06 = 6%

Looting II:
0.06 + 0.01 × 1 = 0.07 = 7%

Looting III:
0.06 + 0.01 × 2 = 0.08 = 8%
```

Обрати внимание: `base` здесь - шанс именно для Looting I, а не шанс без Looting.

Без Looting используется отдельное поле:

```json
"unenchanted_chance": 0.05
```

Это важный вопрос ученику:

> Почему мы не поставили base = 0.05?

Потому что `base` относится уже к первому уровню зачарования.

---

## Шаг 2. Улучшаем шанс кальцита

### Было

```json
"conditions": [
  {
    "condition": "minecraft:random_chance",
    "chance": 0.10
  }
]
```

### Стало

```json
"conditions": [
  {
    "condition": "minecraft:random_chance_with_enchanted_bonus",
    "enchantment": "minecraft:looting",
    "unenchanted_chance": 0.10,
    "enchanted_chance": {
      "type": "minecraft:linear",
      "base": 0.12,
      "per_level_above_first": 0.02
    }
  }
]
```

Здесь идея та же, но прирост больше.

Получаем:

```text
без Looting:
10%

Looting I:
12%

Looting II:
14%

Looting III:
16%
```

Формула:

```text
Looting I:
0.12 + 0.02 × 0 = 0.12

Looting II:
0.12 + 0.02 × 1 = 0.14

Looting III:
0.12 + 0.02 × 2 = 0.16
```

---

## Почему блок и кальцит получают разные бонусы

Блок аметиста ценнее и должен оставаться более редким:

```text
5 → 6 → 7 → 8%
```

Кальцит менее ценный:

```text
10 → 12 → 14 → 16%
```

Это уже не вопрос синтаксиса. Это игровой баланс.

Вопрос ученику:

> Почему нельзя просто сделать Looting III = 50% на блок аметиста?

Потому что тогда редкий ресурс быстро перестанет быть редким, а зачарование станет слишком сильным.

## Что в итоге делает Looting у нашего Crystal Spider

Теперь Looting влияет сразу на ДВЕ разные вещи.

### 1. Количество обычного дропа

```text
без Looting → 1-3 осколка
Looting I   → 2-4
Looting II  → 3-5
Looting III → 4-6
```

### 2. Шанс редкого дропа

```text

II           → 7%
III          → 8%

CALCITE
без Looting → 10%
I            → 12%
II           → 14%
```

Очень полезная схема для доски:

```text
                 LOOTING

          ┌─────────┴─────────┐
          ↓                   ↓

```

Это уже хороший пример того, что одно зачарование может влиять на разные параметры механики.

## Новые строки с учебными комментариями

В рабочий JSON нельзя вставлять `// комментарий`, поэтому ниже показана УЧЕБНАЯ версия. Её не нужно копировать в Minecraft как JSON.

### Блок аметиста

```text
"condition": "minecraft:random_chance_with_enchanted_bonus", // НОВОЕ: шанс зависит от зачарования
"enchantment": "minecraft:looting",                          // НОВОЕ: смотрим Looting
"unenchanted_chance": 0.05,                                 // без Looting = 5%

  "type": "minecraft:linear",                               // растёт равномерно по уровням

  "per_level_above_first": 0.01                             // каждый следующий уровень +1%
}
```

### Кальцит

```text
"condition": "minecraft:random_chance_with_enchanted_bonus", // НОВОЕ
"enchantment": "minecraft:looting",                          // проверяем Looting
"unenchanted_chance": 0.10,                                 // без Looting = 10%
"enchanted_chance": {
  "type": "minecraft:linear",
  "base": 0.12,                                             // Looting I = 12%
  "per_level_above_first": 0.02                             // Looting II +2%, III ещё +2%
}
```

## Как тестировать

Редкие проценты неудобно проверять вручную.

Сначала проверяем, что JSON загрузился и обычный дроп работает.

```json
"unenchanted_chance": 0.10,
```


Так разницу легко увидеть.


и:

```text

```

> Сначала тестируем механику на больших значениях, потом тестируем баланс на настоящих.
